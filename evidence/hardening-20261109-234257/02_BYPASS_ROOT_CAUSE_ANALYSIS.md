# 2. Root-cause analysis of all bypass classes

## 2.0 Correcting the count: what "67 bypass cases" actually means

The figure "67 demonstrated command-filter bypass cases" in the mandate came from my November 9 summary, and **it was wrong**. The November 9 audit ran **69 probes**: 60 single commands, among them 2 baselines (`rm -rf build`, `git push`), and 9 chains. That makes **67 attack probes**, not 67 bypasses.

Re-classified with the same inputs against V2 `e60278f` (`evidence/probe-compare/probe-compare.tsv`, generated by `scripts/probe-compare.ts`):

| Outcome on V2 `e60278f` | Count |
|---|---|
| Probes where a correct policy should block, and V2 **allowed** (text-decidable bypass) | **33** |
| Probes V2 correctly blocked | 19 (17 attacks + the 2 baselines) |
| Probes that are legitimate or **not decidable from command text** (script file, `npx`, `npm run` without a body, PATH change, tools hidden by `--tools`) | 17, of which 15 are residual risk (class S/N) and 2 are legitimate (`npm test`, the heredoc false-positive check) |
| **Total** | **69** |

So V2 had **33 text-decidable bypasses**, plus **15 structurally undecidable cases** that only OS isolation can address. On the V2.1 branch, the text-decidable bypasses fall to **0 of 33**, with **0 regressions** on the legitimate probes and 82 new unit tests. The 15 structural cases remain, by design.

## 2.1 The single root cause

> **The worker and the supervisor run as the same Windows principal, and the only thing between them is a classifier of command TEXT.**

A text classifier can only see what the model types. It cannot see:
- what a program does once started: scripts, interpreters, `npm` scripts, compiled tools, downloaded packages;
- values computed at run time: variables, substitutions, decoding;
- the file system state at run time: globs, relative paths, the current directory.

Because the OS identity is shared, nothing stops the effect, so every gap in the classifier is a full bypass. The classes below are symptoms; **class S is the irreducible one**.

## 2.3 Why the residual classes cannot be closed by more rules

- **Rice's theorem in practice.** "Does this program delete files outside the workspace / open `agent.db` / read the credentials file?" is undecidable for arbitrary programs. A worker that can write and run a file can do anything its OS identity can do.
- **Adding rules raises false positives.** Content scanning of every written file for `rmSync`/`DROP TABLE`/`push` would block ordinary engineering. The V2 pilot already produced 5 false-positive approvals from text matching (defect A2). V2.1 therefore restricts content checks to markers with no legitimate use in a customer project: agent-control artefacts, credentials, the agent's own paths.
- **The guards themselves belong to the worker.** Environment variables, file modes and files in `%LOCALAPPDATA%` are all under the control of the user the worker runs as.

**Therefore:** the V2.1 text hardening is worth shipping (it closes every *accidental* and *low-effort* path we found, and fixes two real logic defects, A and M). It must be described as a **guardrail**. Approvals become a security boundary only with the OS isolation in document 3.

## 2.4 False-positive risk introduced by V2.1 (honest list)

| Change | Possible false positive | Mitigation |
|---|---|---|
| Env-dump denial (`env`, `printenv`, `set` alone) | A worker debugging its environment | Rare; deny reason tells the model to continue; `echo $VAR` for a specific non-secret variable still works |
| Command substitution in command position denied | Generated build scripts sometimes use `$(which node) …` | Workers can call the program by name; reported as a hard deny (no approval loop) |
| `git config core.hooksPath` needs approval | Husky set-up typed by hand | `npm install` running husky is not affected (the policy sees only the typed command) |
| Write/Edit content mentioning `agent.db`, `apr_…`, `ELEVARIQ_WORKER`, `.credentials.json` | A customer project that legitimately uses these names | Unlikely in customer projects. **Do not** point workers at the agent's own repository |
| `schtasks`, `reg add`, `setx`, `netsh` need approval | Projects that script Windows set-up | Approval flow (owner decides) |
| `cd` outside the workspace + bare words | `cd /tmp && rm x` is unaffected; only words that resolve into protected paths deny | — |
